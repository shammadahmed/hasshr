Hasshr: Product Requirements Document

Version: 0.3 (hackathon draft) · Author: Hammad Ahmed · Status: Draft

1. Overview

Hasshr is a Python CLI agent that lets anyone operate their computer by describing what they want in plain language, instead of typing Linux, macOS, or Windows commands. An LLM acts as an agent: it plans, runs real commands and tools, verifies the result, and reports back in simple language.

pip install hasshr
hasshr "find my largest files"
hasshr            # interactive mode

One-line pitch: Prompt your operating system, with safety controls that make it usable by non-programmers.

1.1 Hackathon fit

Required skill How Hasshr covers it
Generative AI LLM turns intent into plans, commands, and plain-language explanations
Agentic AI Tool-calling loop that acts on the machine and observes results
Multi-Agent Systems Planner, Executor, and Verifier agents (Section 7)
AI Workflows Plan → Approve → Execute → Verify → Log pipeline
Business Process Automation Repeatable tasks (e.g. organize folders, batch updates)

At least two are required; this design targets four.

2. Problem & Opportunity

  • The terminal is powerful but intimidating. Many users avoid it, or paste commands they don't understand.
  • Existing AI terminal tools (Claude Code, Gemini CLI, Open Interpreter, Warp, ShellGPT) mostly target developers and give little control over how much the agent may do.
  • Non-programmers still need tasks like organizing files, updating software, or fixing system settings, and cannot judge whether a generated command is safe.

Opportunity: a terminal agent designed for non-programmers, with a configurable trust model, full-system capability, and an audit/undo trail.

3. Goals & Non-Goals

Goals

  1. Cover the full range of terminal use: files, packages, services, system settings, drivers, updates, bootloader, networking.
  2. Work across Linux, macOS, and Windows.
  3. Let the user control autonomy through three permission modes.
  4. Explain every action in plain language.
  5. Be installable with one pip command and usable in under a minute.
  6. Keep an audit log and, where possible, undo.
  7. Diagnose and fix real system problems through guided trial and error (Troubleshooting Cases), with a change journal that allows rollback and a minimal final fix.
  8. End a Case honestly: when no fix exists (e.g. a known upstream kernel bug), say so with evidence, confidence levels, and ranked workarounds, instead of trying changes indefinitely.

Non-Goals (v0.1)

  • GUI or web interface.
  • Voice input.
  • Remote or multi-machine management.
  • Guaranteed undo for irreversible system operations (drivers, GRUB, updates).
  • Training or fine-tuning custom models.

4. Target Users

Persona Description Key need
Non-programmer (primary) Student, office worker, family member Get tasks done without learning commands; feel safe
Casual power user Knows some commands, forgets syntax Speed; fewer lookups
Developer / sysadmin Comfortable in terminal auto mode, scripting, own model/provider

5. Core User Stories

  1. As a non-programmer, I want to say "put all PDFs in Downloads into a folder called PDFs" and see it done and verified.
  2. As a user, I want to see a plan and approve it before anything risky happens.
  3. As a user, I want to choose whether Hasshr asks about everything, only risky actions, or nothing.
  4. As a user, I want to undo a file move or delete.
  5. As a user, I want to search the web and have results listed and opened in my browser.
  6. As a user, I want to copy text and just get a confirmation.
  7. As an advanced user, I want to ask for sudo, package, or GRUB tasks and have the agent handle them with appropriate warnings.
  8. As a user, I want to use my own API key or a local model.
  9. As a user with a recurring system problem (e.g. no sound after boot on Ubuntu), I want the agent to diagnose it, try fixes one at a time, and revert anything that doesn't work.
  10. As a user, I want to see exactly what was changed to fix my problem, and be able to undo all of it.
  11. As a user whose problem has no real fix (e.g. a mic broken by a Linux kernel regression), I want the agent to tell me that clearly, show the evidence, and list my options (such as rolling back the kernel), including what each option costs me.

6.4 Risk Classification

Risk is decided by deterministic rules first, combined with the LLM's own rating; the higher of the two wins.

Level Examples Behavior by mode
Safe (read-only) ls, cat, df, find, ps, git status Never asks
Moderate (reversible changes) Create folders, move/copy files, git commit, install user-level packages Asks in ask-all only
Sensitive rm -r, sudo, chmod -R, chown, package install/remove/upgrade (apt, dnf, brew, winget), service control, firewall, user management, writes under /etc or system dirs, curl | sh, driver installs, GRUB changes Asks in ask-all and ask-sensitive
Blocked rm -rf /, dd onto disk devices, mkfs on mounted drives, fork bombs, wiping bootloader without a flag Refused in every mode unless --allow-dangerous is set
ID Requirement Priority
F-16 Parse commands with shlex and a pipeline-aware analyzer (pipes, &&, ;, subshells, bash -c, sudo wrapping) P0
F-17 Anything the classifier cannot parse or identify is treated as Sensitive P0
F-18 Rule set is data-driven (YAML) so it can be updated without code changes P1
F-19 Hard-block list cannot be overridden by the LLM or by prompt text P0

6.8 Troubleshooting Cases (v0.2)

A Case is a long-running, stateful task for fixing a problem through diagnosis and trial and error. Example: "My Ubuntu laptop shows Dummy Output after boot and I have to run sudo alsa force-reload every time."

Case lifecycle

  1. Define "fixed". Before changing anything, agree on a measurable success test (e.g. pactl list sinks short shows a real sink, not auto_null, after a reboot).
  2. Diagnose (read-only). Collect evidence with no changes: aplay -l, pactl info, dmesg, journalctl, lspci, relevant config files.
  3. Hypothesis plan. Produce a ranked list. Each entry has: the proposed change, why it might work, reversibility (Full / Partial / None), required reboot, and the source of the idea (own reasoning, official docs, or web result).
  4. Try one hypothesis at a time. Apply, test, and roll back if it fails before trying the next. Changes are never stacked.
  5. Clean-room confirm. When something works, revert everything, reapply only the winning change, and re-test. The result is a minimal fix, with no leftover experiments.
  6. Report. One of four outcomes (see Case outcomes), with the root cause as far as known, the evidence, the final change or the ranked options, what was reverted, and the one command to undo any change made.
ID Requirement Priority
F-32 hasshr case "<problem>" (or automatic escalation from a normal prompt) starts a Case with a persistent case ID P0
F-33 The agent must define a success test and get user approval for it before making any change P0
F-34 Diagnosis phase is strictly read-only; any state-changing command is blocked until the plan is approved P0
F-35 The plan is shown as a ranked hypothesis list with reversibility labels; the user can reorder, skip, or add ideas P0
F-36 Hypotheses are applied one at a time, with an automatic test and rollback after each failure P0
F-37 A typed edit_file tool (append, replace, insert, create) is used for config changes, never an interactive editor like nano driven by the LLM P0
F-38 Clean-room confirmation (revert all, reapply the winner, re-test) before a Case can be marked fixed P1
F-39 Web or forum advice (Stack Overflow, Ask Ubuntu, wikis) is treated as untrusted input: shown with its source, and every command from it goes through the risk classifier P0
F-40 Safety limits per Case: max attempts (default 8), and a user check-in after 3 consecutive failures, even in auto mode P0
F-41 In auto mode, steps labeled reversibility None still require explicit approval P0
F-42 Case state survives reboots: hasshr resume runs the success test and continues or rolls back P1
F-43 Final report is saved as a markdown file for the user's records P2

Change Journal (the basis for rollback)

  • Before every file edit: save a timestamped backup, record the SHA-256 hash and a diff.
  • Before and after every attempt: snapshot package list, service enabled/active state, kernel module parameters, and files created or removed.
  • Record every command with its exit code and output (secrets redacted).
  • Rollback replays the journal in reverse order and verifies the restored state against the snapshot.
ID Requirement Priority
F-44 Each Case has its own journal, stored locally and append-only P0
F-45 hasshr case undo <id> rolls back all or selected attempts P0
F-46 Rollback verification: compare restored file hashes and package/service state against the pre-case snapshot, and report any difference P1
F-47 Each step is labeled with reversibility before it runs P0

Reversibility levels

Level Examples Rollback
Full Config file edits, created files, service enable/disable, module parameters Restore from backup/snapshot
Partial Package install/removal (config and dependencies may differ), apt upgrade of specific packages Reverse the action, but report differences
None Firmware flashing, kernel/driver replacement, bootloader changes, data deletion without backup Not reversible; warn, require approval, and suggest a system snapshot or backup first

Case outcomes & evidence rules

Not every Case ends in a fix. A Case must end in exactly one of these outcomes:

Outcome Meaning
Fixed The success test passes after a clean-room confirmation
Workaround The problem is avoided but not truly fixed (e.g. booting an older kernel)
Known issue, no fix available Matches a documented upstream bug; options are listed with trade-offs
Unresolved Evidence gathered and attempts exhausted; next steps and what was ruled out are listed

Every finding in the report carries a confidence label:

  • Confirmed: reproduced or verified by a test on this machine.
  • Likely: matches a documented report plus this machine's hardware IDs and kernel version.
  • Speculation: plausible but unverified.
ID Requirement Priority
F-48 Every Case ends with one of the four outcomes and an evidence report P0
F-49 Findings are labeled Confirmed / Likely / Speculation; web or forum claims are never presented as Confirmed without a local test P0
F-50 Before concluding "known kernel regression", the agent proposes a one-time boot of the previous kernel (e.g. grub-reboot or the distro equivalent) and runs the success test; this does not change the default boot entry P0
F-51 Evidence section cites sources (bug tracker, mailing list, distro tracker, forum thread), affected versions, and the machine's own uname -r and hardware IDs that match them P0
F-52 Report lists what was ruled out and why, so the user does not repeat it P1
F-53 For "no fix" outcomes, options are ranked with cost and reversibility, e.g. roll back kernel (Partial; keep the newer kernel installed), pin with apt-mark hold (Full), wait for a patched kernel P0
F-54 Advice such as "changing distro won't help" is checked against the kernel version and patches the alternative would actually ship (e.g. LTS vs HWE kernels) before it is stated P1
F-55 The agent stops and reports instead of continuing once all credible hypotheses are exhausted or the attempt limit is reached P0
F-56 Optional watch mode: re-check when a new kernel or package version is available and report whether the issue is fixed upstream P2

Example Case flow (audio)

You > My sound shows Dummy Output after every boot. Fix it.

Agent > Starting Case #3. Success test: after reboot, `pactl list sinks short`
        shows a real sink.

✓ Diagnosed (read-only): sound card detected, but the driver loads late at boot

Plan (ranked):
  1. Add `options snd-hda-intel ...` in /etc/modprobe.d/   [Reversibility: Full]
  2. Reinstall alsa-base / pulseaudio packages              [Partial]
  3. Pin a kernel module load order via initramfs            [Partial]

Try #1? [y]es [n]o [e]dit plan

✓ Backed up /etc/modprobe.d/alsa-base.conf
✓ Edited file (diff saved)
… Reboot required. Run `hasshr resume` after restarting.

Example Case flow (microphone, "known issue" outcome)

You > My microphone stopped working. Fix it.

Agent > Starting Case #4. Success test: `arecord` records audible input
        from the built-in mic.

✓ Diagnosed (read-only): mic detected, no audio captured, errors in dmesg
✓ Tried 3 config fixes, one at a time; all rolled back, none worked

Finding (Likely): matches a reported regression in kernel 6.x on your
hardware (sources: bug tracker thread, distro forum).
Test: boot the previous kernel once (default boot unchanged). Run test? [y/n]

✓ Mic works on the previous kernel. Finding upgraded to Confirmed.

Outcome: KNOWN ISSUE, NO FIX AVAILABLE
Options:
  1. Boot the previous kernel      [Reversibility: Partial; newer kernel stays installed]
  2. Pin the kernel (apt-mark hold) [Full]
  3. Wait for a patched kernel      [use `hasshr watch` to be notified]
Note: switching distro would not help unless it ships a different kernel.

7. Agent Architecture

User prompt
   │
   ▼
┌─────────┐   plan    ┌──────────────┐  approved steps  ┌──────────┐
│ Planner │ ───────▶  │ Permission & │ ───────────────▶ │ Executor │
│  agent  │           │ Risk Engine  │                  │  agent   │
└─────────┘           └──────────────┘                  └────┬─────┘
     ▲                                                       │ results
     │              ┌──────────┐   pass / fail + fixes       ▼
     └───────────── │ Verifier │ ◀───────────────────────────┘
        replan      │  agent   │
                    └────┬─────┘
                         ▼
                 Summary + audit log + undo journal
  • Planner: converts the request into ordered steps, picks tools, and explains each in plain language.
  • Risk Engine (non-LLM): classifies each step and enforces the active permission mode and hard blocks.
  • Executor: runs approved steps through tools and captures output and exit codes.
  • Verifier: checks the actual system state against the goal; triggers replanning on failure (max 3 retries).

Case mode: a Case reuses these agents with an added Diagnostician (read-only evidence gathering and hypothesis ranking) and a Journal Keeper (non-LLM component that records backups and snapshots, and executes rollbacks). The Planner may only propose; the Journal Keeper and Risk Engine decide what actually runs. The Verifier also reviews each Case conclusion: it checks that confidence labels match the evidence and that "known issue" claims were tested locally where possible.

Loop limits: max steps per task (default 25), max retries, and timeouts per command, to prevent runaway behavior.

8.2 Approval prompt (sensitive action)

Agent > I need to install the NVIDIA driver.

  Command:  sudo apt install nvidia-driver-550
  Effect:   Installs a graphics driver and may require a reboot.
  Risk:     SENSITIVE   Undo: not available

  Run this? [y]es  [n]o  [e]dit  [a]lways this session

8.3 UX principles

  • Plain language first, raw commands second.
  • Never hide what will run; always show the exact command on approval.
  • Short output; details available via /log.
  • Errors explain what went wrong and what to try next.

9. Technical Requirements

  • Language: Python 3.10+
  • Distribution: PyPI package hasshr (verify name availability early), entry point hasshr
  • Suggested libraries: typer or click (CLI), rich (output, prompts), litellm (providers), pyperclip, built-in webbrowser, send2trash, shlex, platformdirs, keyring, pyyaml
  • Platforms: Linux and macOS first-class; Windows (PowerShell/CMD) supported via shell adapters
  • Storage: local config, audit log, and undo journal in the platform config directory
  • Privacy: no telemetry by default; only the prompt and necessary context go to the chosen model

12. Risks & Mitigations

Risk Impact Mitigation
LLM generates a destructive command High Deterministic classifier, hard blocks, confirmation, Trash/backup
Prompt injection via web or file content High Untrusted-data labeling, escalation rules, no auto-running copied commands
Misclassification of complex shell Medium Unknown = Sensitive; pipeline-aware parsing; test suite
User enables auto without understanding High Explicit acknowledgment, warning, hard blocks remain
Irreversible system changes (GRUB, drivers) High Clear "no undo" labeling, dry-run options, audit log
Cross-platform command differences Medium Environment detection, typed tools, per-OS prompts
PyPI name conflict or crowded market Medium Check name now; differentiate on non-programmer UX and safety
API cost / latency Low Provider choice, local models, step limits
Trial and error leaves the system worse than before High One change at a time, rollback after each failure, clean-room confirmation, journal with verification
"Full undo" promised but not possible (drivers, firmware, GRUB) High Reversibility label before every step, approval required for None-level steps, suggest snapshots
Bad advice from forums or web results Medium Untrusted-input handling, source shown to the user, same risk classification as any command
Agent declares "known issue, no fix" too early or wrongly High Confidence labels, one-time boot test of the previous kernel, cited sources, Verifier review of conclusions
Kernel rollback or pinning breaks drivers (e.g. DKMS modules) or leaves the system without security updates Medium Keep the newer kernel installed, use reversible holds, warn about security implications, document how to undo
Rollback itself fails or leaves partial state Medium Hash/snapshot verification after rollback, clear report of differences, manual recovery instructions

13. Roadmap

Phase 1: Hackathon MVP (P0)

  • CLI one-shot + interactive mode
  • Typed file tools + run_shell
  • Three permission modes + rule-based classifier + hard blocks
  • Planner/Executor/Verifier loop
  • Audit log, Trash-based undo for file operations
  • One provider + environment detection
  • Polished demo scenario (Downloads organizer)

Phase 2: Beta

  • Web search + browser opening, clipboard tool
  • Multi-provider and local model support
  • YAML-editable rules, /log, session memory
  • Windows adapter polish, dry-run support
  • PyPI release
  • Troubleshooting Cases: diagnosis, hypothesis plan, one-at-a-time trials, change journal, rollback, hasshr resume
  • Case outcomes (Fixed / Workaround / Known issue / Unresolved) with confidence-labeled evidence reports and one-time previous-kernel testing

Phase 3: Later

  • Saved routines ("every Friday, clean Downloads")
  • Plugins/custom tools
  • Safer sandboxing (containers, snapshots such as Btrfs/ZFS/Time Machine integration)
  • Optional voice and GUI wrapper
  • Watch mode: notify when an upstream fix lands in a newer kernel or package

14. Open Questions

  1. Should ask-sensitive allow per-category overrides (e.g. always ask for packages, never ask for file moves)?
  2. How should multi-step plans be approved: all at once, or step by step?
  3. Which snapshot or backup mechanism, if any, to integrate for system-level undo?
  4. What is the policy for logging command output that may contain secrets?
  5. Is --allow-dangerous shipped at all in v0.1, or deferred?
  6. Final package name: confirm hasshr is available on PyPI, or pick an alternative.
  7. Should Cases integrate system snapshots (Btrfs/ZFS/Timeshift/Time Machine) as an extra safety net for None-level steps?
  8. How much of the journal should be shared with the LLM, to limit tokens and avoid leaking sensitive file contents?
  9. Which reproducible failure should the hackathon demo use? A scripted fault in a VM is more reliable than a real hardware issue.
  10. Which sources count as authoritative for "known issue" findings (kernel bugzilla, distro trackers, mailing lists), and how should conflicting reports be handled?
  11. How is a one-time boot of the previous kernel done safely across distros and bootloaders, and what if the machine cannot reboot unattended?
