TermiAI: Implementation Plan (6 Members)

Based on: TermiAI PRD v0.3 · Team: 6 members · Admin: Hammad · Goal: win the hackathon with a polished, complete product

Requirement IDs (F-xx) refer to the PRD. Stages are given as shares of your total time, so they can be mapped to the real deadline once it is known.

1. Principles

  1. Always demo-ready. After every stage the product works end to end. Later stages add depth; they never break earlier demos.
  2. Contracts first. Six people can only work in parallel if the shared interfaces are agreed on day one (Section 4).
  3. Safety is the differentiator. Everything that changes the system passes through the Risk Engine and the Journal. No tool bypasses them.
  4. No risky testing on personal laptops. All sudo, rm, package, and kernel tests run in the shared Ubuntu VM image.
  5. Each member owns tests for their module. A task is Done only with tests, docs, and a reviewed PR.

4. Shared Contracts (defined in S0, owned by M1, changed only by agreement)

Located in termiai/contracts.py.

Structure Key fields Used by
ToolCall / ToolResult name, args, explanation / ok, output, exit_code M1, M3, M4
RiskResult level (Safe, Moderate, Sensitive, Blocked), reasons, source (rules or LLM) M2, M1, M6
Decision allow / ask / refuse, mode, reason M2, M1, M6
Reversibility Full / Partial / None, undo_hint M3, M4, M5
JournalEntry id, case_id, step, command, backups, hashes, diff, time M4, M1, M5
Snapshot packages, services, module params, file hashes M4, M5
Hypothesis change, rationale, reversibility, reboot_needed, source M5, M6
CaseState id, success_test, phase, attempts, outcome, findings M5, M1, M6
Finding statement, confidence (Confirmed / Likely / Speculation), evidence M5, M6

Module APIs (signatures agreed in S0):

classify(command: str, ctx) -> RiskResult            # M2
decide(risk: RiskResult, mode, ctx) -> Decision      # M2
Tool.run(args, ctx) -> ToolResult                    # M3 (every tool declares Reversibility)
journal.record(entry) / journal.backup_file(path)    # M4
journal.rollback(case_id, upto=None) -> RollbackReport   # M4
snapshot.take(scope) / snapshot.diff(a, b)           # M4
case.start / case.step / case.finish                 # M5
llm.complete(messages, tools, model) -> response     # M6

Rule: the Executor (M1) never runs a tool directly. The path is always classify → decide → (ask user) → journal.before → tool → journal.after → verify.

7. Working Rules

  • Repo: main is always runnable. Feature branches named m2/classifier-pipes; PRs reviewed by the paired member within 24 hours.
  • Daily 10-minute standup: done, doing, blocked. Blockers go to M1 the same day.
  • Contract changes: announced in the team chat and approved by M1 before merging.
  • CI: lint and tests must pass. No direct pushes to main after G1.
  • Test VM: one shared Ubuntu image with snapshots; reset after destructive tests.
  • Secrets: API keys never committed; use .env and a shared secret manager.
  • Load check: at G1 and G3, review actual workload and rebalance without drama.

12.0 Shared Context Prompt (everyone pastes this first)

You are helping me build TermiAI, a Python 3.10+ command-line agent published
as `pip install termiai`. Users type plain-language requests (e.g. "find my
largest files" or "my mic stopped working, fix it") and an LLM agent plans,
runs real commands/tools on their machine, verifies the result, and reports in
simple language. Target users include non-programmers.

Key features:
- Three permission modes: ask-all, ask-sensitive (default), auto.
- Risk levels: Safe, Moderate, Sensitive, Blocked. Deterministic rules decide
  first; the LLM's rating can only raise the level. Unparseable commands count
  as Sensitive. Hard-blocked commands (rm -rf /, dd to disk devices, mkfs on
  mounted drives) are refused in every mode.
- Agents: Planner (plans steps), Executor (runs tools), Verifier (checks real
  system state). Typed tools (list/move/copy/edit files, web search,
  clipboard) are preferred; `run_shell` handles everything else.
- Change journal: backups with hashes, snapshots, reverse-order rollback,
  append-only audit log, and a reversibility label (Full/Partial/None) for each
  step shown BEFORE it runs.
- Troubleshooting Cases: define a success test, read-only diagnosis, ranked
  hypotheses, one change at a time with rollback after each failure,
  clean-room confirmation, and an honest outcome (Fixed, Workaround, Known
  issue/no fix, Unresolved) with Confirmed/Likely/Speculation labels.

Execution pipeline (no tool may bypass it):
classify -> decide -> (ask user) -> journal.before -> tool -> journal.after -> verify

Rules for you:
- Use the shared data structures in termiai/contracts.py. Do not change them
  without telling me first.
- Ship a working STUB of my module's public API first so teammates can
  integrate, then replace it with the real implementation.
- Write type hints, docstrings, and pytest tests for everything.
- Never run destructive commands (rm, sudo, package or kernel changes) on my
  real machine; assume a disposable Ubuntu VM.
- Never log or send secrets. sudo passwords must never pass through the LLM.
- Work in small steps: propose the file layout and wait for my approval, then
  implement, then test. If the spec is ambiguous, ask me instead of guessing.

I own the module described next.

12.2 M2: Safety engine

ROLE: Safety engine owner (risk classifier, permission modes, injection defense).

BUILD:
1. classify(command, ctx) -> RiskResult using shlex plus a pipeline-aware
   analyzer: pipes, &&, ||, ;, subshells, `bash -c`, sudo/env wrapping,
   redirects to system paths. Anything unparseable or unknown = Sensitive.
2. Data-driven rules in rules.yaml (levels, patterns, reasons): rm -r, sudo,
   chmod/chown -R, dd, mkfs, package install/remove/upgrade for apt/dnf/brew/
   winget, services, firewall, users, writes under /etc, curl|sh, GRUB and
   driver changes. Add PowerShell/CMD rules later.
3. Hard-block list the LLM or prompt text can never override.
4. decide(risk, mode, ctx) -> Decision for ask-all, ask-sensitive, auto, plus
   the "always for this session" option. Auto mode still refuses Blocked.
5. Merge LLM risk rating with rules: the higher level wins.
6. Prompt-injection defense: label web results, file contents and command
   output as untrusted data; never auto-run commands copied from web pages;
   escalate risk after untrusted content when a command touches the network
   or system settings.
7. Case rules: during diagnosis only read-only commands are allowed;
   reversibility "None" steps need explicit approval even in auto mode; force
   a user check-in after 3 consecutive failed attempts.

ACCEPTANCE: a labeled corpus of 200+ commands; 100% of hard-block cases
refused; at least 95% of Sensitive cases flagged; parse failures always
Sensitive; injection tests (malicious text in a page or file) never trigger
commands.

START BY: proposing the rules.yaml schema and the test-corpus format.

12.3 M3: Tools & platform

ROLE: Tools and platform owner.

BUILD (every tool declares a Reversibility label and a plain-language
explanation, and returns a ToolResult):
1. Environment detection: OS, distro/version, shell, package manager.
2. Typed tools: list_files, find_files, read_file, move_file, copy_file,
   create_folder, delete_to_trash (use send2trash), with hooks that call the
   journal before and after (journal.backup_file, journal.record).
3. run_shell(command, explanation): timeouts, captured stdout/stderr and exit
   code, and sudo prompts handed directly to the user's terminal (TTY) so the
   password never touches the LLM or logs.
4. edit_file (append, replace, insert, create) with backup before editing. The
   LLM must never drive an interactive editor like nano.
5. search_web (titles + URLs printed in the terminal, selected results opened
   with the webbrowser module), open_url, copy_to_clipboard (confirmation
   only, no echo of content).
6. Read-only diagnostic helpers: logs (journalctl, dmesg), device info,
   package/service state readers, plus data collectors for snapshots.
7. Previous-kernel helper: list installed kernels and boot a chosen one ONCE
   (e.g. grub-reboot) without changing the default entry.
8. macOS and Windows adapters; typed tools must work on all three OSes.

ACCEPTANCE: all typed tools pass tests on Linux first, then macOS and
Windows; no tool changes the system without going through the journal hooks;
sudo password never appears in logs or LLM context.

START BY: proposing the Tool base class and registry, with stubs for
list_files and move_file.

12.4 M4: Journal, undo & audit

ROLE: Journal, undo and audit owner.

BUILD:
1. Append-only journal storage (global and per-case) in the platform config
   dir (platformdirs), using the JournalEntry contract.
2. backup_file(path): timestamped copy, SHA-256 hash, and diff recorded
   before every edit or delete. Deletions go to Trash.
3. Audit log of every prompt, plan, command, approval decision, output and
   exit code, with secret redaction (API keys, passwords, tokens).
4. `termiai undo` and `/undo` for file operations.
5. Snapshots (package list, service enabled/active state, kernel module
   parameters, tracked file hashes) and snapshot.diff(a, b).
6. rollback(case_id, upto=None): replay the journal in REVERSE order, then
   verify the restored state against the pre-case snapshot and return a
   RollbackReport listing any differences.
7. Reversibility labeling data (Full/Partial/None) shown BEFORE a step runs.
   For None-level steps, recommend a backup or system snapshot first.

ACCEPTANCE: rollback of a multi-step case restores file hashes and
package/service state; a rollback that partly fails reports exactly what
remains and how to fix it manually; journal survives crashes (no
half-written entries); tests run in the VM.

START BY: proposing the journal file format and the JournalEntry and
Snapshot fields.

12.5 M5: Troubleshooting Cases

ROLE: Troubleshooting Cases owner.

BUILD:
1. CaseState, Hypothesis and Finding contracts and the lifecycle: define
   success test (user approves) -> read-only diagnosis -> ranked hypothesis
   plan -> try ONE hypothesis at a time with automatic test and rollback after
   each failure -> clean-room confirmation (revert everything, reapply only
   the winner, re-test) -> final report.
2. Prompts for the Diagnostician (evidence gathering using read-only tools)
   and for hypothesis ranking. Each hypothesis includes: change, rationale,
   reversibility, reboot needed, and source (own reasoning, official docs, or
   web). Web/forum advice is UNTRUSTED and still goes through the risk
   classifier.
3. Outcomes: Fixed, Workaround, Known issue/no fix, Unresolved. Every finding
   is labeled Confirmed (tested on this machine), Likely (matches a report
   plus this machine's hardware IDs and kernel), or Speculation. Never present
   forum claims as Confirmed without a local test.
4. Before concluding "known kernel regression", propose a one-time boot of the
   previous kernel, run the success test, and upgrade the finding to
   Confirmed if it works. For no-fix outcomes, give ranked options with cost
   and reversibility (roll back kernel, pin with apt-mark hold, wait for a
   patch). Before saying "changing distro won't help", check which kernel the
   alternative would actually ship.
5. Evidence report: cited sources, affected versions, this machine's
   `uname -r` and hardware IDs, what was ruled out and why. Save as Markdown.
6. `termiai case` command, automatic escalation from normal prompts,
   `termiai resume` after reboot (case state persists on disk), and `watch`
   mode that re-checks for upstream fixes.
7. Demo fixtures (with the CLI owner): a broken service config that is fixable,
   and a simulated kernel regression where a test script fails on the new
   kernel and passes on the older one.

LIMITS: max 8 attempts per case; stop and report when credible hypotheses
are exhausted.

ACCEPTANCE: the fixable fixture ends Fixed with a minimal change; the
regression fixture ends Known issue with a Confirmed finding; failed attempts
are always rolled back before the next one.

START BY: proposing the CaseState machine and one example of a full report.
